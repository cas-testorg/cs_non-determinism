## Findings
- `rlx/core/util/cnm/cnmContext.cc`, `cnmContext::cnmContext` / `~cnmContext` / `getCnm`, with consumers in `ctsutil/ctsCnmUtil.cc` and `icg/ctsICGEstimators.cc`.
  The state in question is the `_nbmUtil` member, plus dependent pointers such as `_nbmContext`. On the `_nbmUtil->isInitialized() == false` path, the constructor deletes `_nbmUtil` and returns without nulling it or completing initialization. The destructor later tests `_nbmUtil` and deletes it again, so a failed CNM initialization yields an established double-delete path. Separately, unchecked callers such as `ctsFastCtsEstimator::doDataCollection()` call `initCnmNetwork()` and `getCnm()` without first checking `isInitialized()`, and `initCnmNetwork()` immediately dereferences `_cnmContext->getNbmContext()->getNbmUtil()`. The local source therefore establishes undefined behavior if CNM init fails: either double free on scope exit, or null/dangling-pointer use in CNM bring-up. Observable impact is a crash or heap corruption during CNM-dependent flows. Nondeterminism is not established, although allocator-dependent manifestation is plausible. Confidence: high. Missing evidence: whether `nbmUtil->isInitialized()` can fail in supported production environments.

- `mscts/msmesh/msSplitTree.cc`, `msSplit::getViolatorPriority`.
  The locals `shortest` and `longest` are initialized to the float sentinel and only assigned inside the loop when a direct sink successor exists and `node->getPathDelay(input, ...)` succeeds. They are then consumed unguarded by `if ((longest - shortest) > skewLimit)`. The relevant execution path is strong: the caller walks upward from each `sinkDriver` through ancestor nodes, so evaluated nodes are not guaranteed to have direct sink successors with valid path-delay data. I did not find a guard or invariant in this function that proves at least one qualifying assignment occurs before the subtraction. That makes this an unsupported initialization path: sentinel state can influence the branch that decides whether a node gets priority `10000` as a skew violator. Downstream impact would be incorrect split prioritization or skipped/incorrect split actions. Undefined behavior is not established from local source; this is an invalid sentinel consumption path rather than a proven language-level UB. Nondeterminism is not established. Confidence: medium-high. Missing evidence: runtime confirmation that real workloads reach this function with zero qualifying sink-delay assignments.

- `ccd/ccdui/ccduiReport.cc`, `ccdRptGlobalQoRCalculator::collectWnsTns`.
  The local `tns` is initialized to `nwmathFloat::getUninitValue()` and then, in the composite-TNS-with-skip-PGs branch, consumed by raw `tns += slack` after only checking `slack < 0`. There is no prior initialization or `isInit()`/`addOrSet()` guard before the first accumulation. This path flows directly into `captureMetrics()`, which pushes the returned TNS/TNHS values into the metric vector used by reporting and downstream QoR consumers. A sibling implementation in `ccd/util/ccdUtil.cc` uses `nwmathFloat::addOrSet()` and normalizes a still-uninitialized TNS to `0.0`, which is strong in-repo evidence that the sentinel is meant to be guarded before accumulation. This is therefore an established invalid read/use on the branch where `_skipPGs` is non-empty and negative slacks are present. Impact: corrupted setup/hold TNS metrics. Undefined behavior is not established. Nondeterminism is not established. Confidence: high. Missing evidence: whether that slow skip-PG branch is exercised in your current flow mix.

- `mscts/mssc/msscGlobal.cc`, `msscGlobal::precomputeBalancePointOffsets`, consumed by `mscts/mssc/msscXformProblem.cc`, `msscXformProblem::getTargetDelay`.
  The state in question is the cached `balancePointOffset`. The cache precomputes `computeMaxTimingArcValue(bpOffset)`, and that helper starts from the uninitialized sentinel and simply returns it if no initialized timing-arc value is seen. `getBalancePointOffset()` then returns `true` whenever the key exists, and `getTargetDelay()` subtracts `balancePointOffset` from `targetLatency` without checking whether the cached float is initialized. This disagrees with the established balance-point semantic in `mscts/msutil/msUtil.cc`, where `getDelayAndOffsetFromBalancePoint()` initializes missing delay/offset to `0.0f` and only replaces them when `isInit()` succeeds. So the cache layer can preserve ΓÇ£no valid offset arcΓÇ¥ as sentinel, while the non-cached path interprets the same situation as zero offset. Impact: MSSC late/early target constraints can be corrupted for endpoints whose balance-point object exists but lacks initialized offset values. Undefined behavior is not established. Nondeterminism is not established. Confidence: medium. Missing evidence: whether `getCtsDelayPoint()` can return `true` for terms/corners whose offset arcs are all uninitialized in current datasets.

## Guarded Patterns
- `mscts/msutil/msUtil.cc`, `getDelayAndOffsetFromBalancePoint()`, is the safe exemplar-equivalent pattern: it normalizes missing balance-point data to `0.0f` and only consumes arc values after `nwmathFloat::isInit()` checks.
- `mscts/msutil/msUtil.cc` / `mscts/msutil/msUtil.h`, `msDRClimits`, appears intentionally sentinel-based and correctly guarded through `hasMax*()` / `isInit()` checks before comparison, matching the exemplar you provided.
- `mscts/mscore/msILatencyInterf.cc`, `getDelay()`, can return an uninitialized sentinel, but the `msTreeReport.cc` consumers I checked only use it after explicit `!nwmathFloat::isUninit(...)` guards.
- `ccd/util/ccdUtil.cc`, `updateQoRFromMap()`, is the correct local model for TNS aggregation: `chooseLesser()` for WNS, `addOrSet()` for TNS, then normalize a still-uninitialized TNS to `0.0`.

## Bottom Line
The strongest issues are the `cnmContext` failed-init path, which establishes real UB if triggered, and the `ccduiReport` TNS aggregation bug, which is a direct sentinel-consumption defect with clear downstream metric impact. The `msSplit::getViolatorPriority()` path is also concerning because the sentinel can directly influence the split/no-split branch, while the MSSC balance-point cache looks like a semantic mismatch that can inject invalid target latencies when cached offset arcs are absent.
