## Findings

1. `msILVioChecker` can derive latency thresholds from an empty path-delay set, then use those thresholds in scoring without validating them.

```419:427:mscts/msmesh/msSplitLat.cc
float
msLatVioChecker::getPathDelayFromHistogram(float pctValue)
{
  dvuAssertRelease(pctValue>=0.0f && pctValue<1.0) ;

  if (_pathDelays.size()==0)
    return nwmathFloat::getUninitValue();

  return _pathDelays[(_pathDelays.size()-1)*pctValue] ;
}
```

```809:830:mscts/msmesh/msSplitLat.cc
void
msILVioChecker::computeStatus(msTreeNode* node, msILVioChecker::ILNodeStatus& status)
{
  status.node = node ;
  if (!node->getPathDelay(node->getClock(), node->getCorner(), status.longLat, status.shortLat)) return;

  // ...

  float shortestTh = getPathDelayFromHistogram(0.01)+0.001 ;
  float longestTh  = getPathDelayFromHistogram(0.95)-0.001 ;

  float targetLatency = getData().getTargetLatency(node->getClock(), node->getCorner()) ;
  status.lpThreshold = std::max(targetLatency, longestTh) ;
  status.spThreshold = std::min(targetLatency, shortestTh);
}
```

- File/symbols: `mscts/msmesh/msSplitLat.cc` in `msLatVioChecker::msLatVioChecker()`, `msLatVioChecker::getPathDelayFromHistogram()`, `msILVioChecker::computeStatus()`, and `msILVioChecker::ILNodeStatus::computeCost()`. Supporting collector is `mscts/mscore/msTreeReport.cc` in `populatePathDelays()`.
- State in question: `_pathDelays`-derived threshold values, especially `lpThreshold` and `spThreshold`.
- Establishment path: the checker constructor populates `_pathDelays` by walking all trees and collecting sink delays. If nothing is collected, it does not fail or mark the checker unusable; it just skips sorting and continues.
- Consumer: `computeStatus()` immediately does arithmetic on the sentinel return values and stores them into `status.lpThreshold` / `status.spThreshold`. Later, `ILNodeStatus::computeCost()` compares `longLat > lpThreshold` without checking that `lpThreshold` is initialized.
- Guard/mitigation: none at the checker level. This stands out because nearby code that uses `populatePathDelays()` in `msSplit.cc`, `msSplitTree.cc`, `msSize.cc`, and `msRelocator.cc` explicitly checks `pathDelays.empty()` before deriving thresholds.
- Local-source conclusion: the invalid-consumer chain is established if `_pathDelays` is empty. What is not fully established from local source alone is the exact runtime condition that leaves the checker with no collected path delays during a supported latency-optimization run.
- Downstream impact: bad thresholds can distort violation cost calculation, which can in turn affect node ranking and split/sizing choices during latency optimization.
- Undefined behavior: not established from source alone. This is a semantically invalid sentinel-use bug; whether it also becomes UB depends on `nwmathFloat` sentinel semantics outside this repo.
- Nondeterminism: not established.
- Confidence: medium-high.
- Missing evidence: a concrete runtime path showing latency optimization entered with trees present but zero collected path delays, and the exact numeric/NaN semantics of `nwmathFloat::getUninitValue()`.

2. `msTapSynthesis::latencyViolation()` can compare an aggregate sentinel latency against the target without proving that any sink latency was ever computed.

```156:194:mscts/mstap/msTapEst.cc
bool
msTapSynthesis::latencyViolation(cstrClock clock, cstrCorner corner, VerboseLevel verbose)
{
  // ...

  bool status = estimateLatency(clock, corner, false /*fast_mode*/, verbose);
  if (!status) {
    return status;
  }

  float maxLat = nwmathFloat::getUninitValue();
  TermFloatMapType::const_iterator it = _allSinkLatencies.begin();
  for (; it != _allSinkLatencies.end(); ++it) {
    const TermFloatType &termLat = *it;
    float lat = termLat.second;
    if (nwmathFloat::isInit(lat)) {
      nwmathFloat::replaceValueIfGreater(maxLat, lat);
    }
  } // end for sink
  bool violation = maxLat > target;

  // ...
  return violation;
}
```

- File/symbols: `mscts/mstap/msTapEst.cc` in `msTapSynthesis::getLatencies()` and `msTapSynthesis::latencyViolation()`, with downstream control use in `mscts/mstap/msTapSynthesis.cc`.
- State in question: aggregate `maxLat`.
- Establishment path: `getLatencies()` resets all entries in `_allSinkLatencies` to the uninitialized sentinel and only overwrites an entry when `getPhaseDelay()` succeeds, `getClockArrival()` succeeds, and `longest` is initialized.
- Consumer: after the scan, `latencyViolation()` performs `maxLat > target` even if no entry ever passed the `isInit(lat)` guard.
- Guard/mitigation: none for the ΓÇ£all sinks invalid / no sink latencies collectedΓÇ¥ case.
- Relevant execution path: `msTapSynthesis` uses `latencyViolation()` as the branch condition while searching for the tap count, so a bad aggregate value can steer the upper-bound search and the later binary search of tap count.
- Local-source conclusion: the aggregate sentinel can reach a branch condition. The missing piece is runtime proof that `estimateLatency()` can succeed while still leaving all sink latencies unset for a supported design.
- Downstream impact: wrong tap-count decisions and misleading user-facing reporting such as `Estimated latency: nan`.
- Undefined behavior: not established.
- Nondeterminism: not established.
- Confidence: medium.
- Missing evidence: the contract/implementation details of the lower-level arrival/phase-delay APIs and a runtime case where `estimateLatency()` returns success but produces no initialized sink latency.

## Mitigated Patterns

I did **not** elevate the exemplar `msDRClimits` pattern. Its constructor in `mscts/msutil/msUtil.cc` seeds float members and vectors with a sentinel, but its main consumers such as `isLenOk()`, `isCellEmOk()`, `isStageDelayOk()`, and `violates()` consistently gate use with `nwmathFloat::isInit(...)`. That matches the ΓÇ£intentional sentinel with required guardΓÇ¥ pattern you described.

I also checked `getTightestOffsetFromBalancePoint()` in `mscts/msutil/msUtil.cc`. Although the caller initializes `delay`/`offset` to `getUninitValue()`, the callee immediately overwrites both out-params with `0.0f` before any early return, so that path is effectively mitigated.
