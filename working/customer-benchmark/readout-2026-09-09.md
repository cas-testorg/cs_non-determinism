# CTS Non-Determinism Evaluation — Preliminary Findings & Next Steps

## Opening / framing

The goal of this exercise was to test the existing Synopsys nondeterminism workflow in Cursor both **without CoreStory** and **with CoreStory**, while keeping the prompt and CTS scope as consistent as possible.

The main conclusion is that we learned useful things about the workflow and CoreStory's qualification value, but the local environment was **not controlled enough to support a final apples-to-apples token/cost claim**. The decisive quantitative benchmark still needs to be run by Synopsys in their controlled environment.

---

## What we ran

### TC-001 — Initial baseline pilot

- Same CTS repository and ND prompt.
- CoreStory disabled.
- Run hit disk exhaustion and required human intervention.
- Expected `scan_nd.py` / `render_report.py` scripts were not installed, so Cursor substituted its own local search/triage workflow.
- Cursor UI showed Claude Opus 4.8, but Usage telemetry reported `auto`.
- Approximately 3.69M total tokens were associated with the two large benchmark events, much of it cache-read context.

**Takeaway:** useful diagnostic evidence, but not a valid final baseline.

### TC-001A — Clean baseline control

- Disk issue resolved.
- CoreStory disabled.
- Same user prompt and CTS scope.
- Explore Subagent Model was disabled and the visible model was constrained.
- Cursor nevertheless changed execution strategy and created multiple child analysis sessions.
- Stage 1 produced **4,535 hits across 817 files**.
- Final report promoted **1 HIGH + 6 MEDIUM** findings.

**Takeaway:** completed baseline, but Cursor orchestration was not fully controllable.

### TC-001B — CoreStory-assisted discovery / qualification

- Same user prompt and CTS scope.
- CoreStory MCP enabled.
- CoreStory governing rule enabled.
- Synopsys skill installation left unchanged.
- Cursor reused prior local ND artifacts, so this was not a clean independent discovery run.
- CoreStory-assisted caller/build/observability checks reduced the final promoted set to **0 HIGH + 0 MEDIUM** confirmed equivalent-run defects.

**Takeaway:** strong qualification / false-positive-reduction signal, but not a clean A/B economics test.

---

## The most important finding

The strongest preliminary signal was **quality of qualification**, not token reduction.

A good example is the baseline HIGH finding in `ctoFlowClone.cc`:

- Baseline analysis saw address-ordered `std::set<ndmTerm*>` iteration and promoted it as a real HIGH issue.
- CoreStory-assisted analysis checked the production build and found `ctoFlowClone.cc` was **not in `ctscto/Master.make`**.
- The live production path instead uses `ctoRestruct.cc` and `termSetType`, which uses `ndmObjPtrCmpType` for deterministic ordering.

Another HIGH candidate used `std::random_device`, but deeper analysis showed its only caller was commented out.

**Message to emphasize:**

> CoreStory did not simply produce a larger defect list. It added application context that changed which findings actually survived build, reachability, and observability checks.

That is the distinction between **pattern matching** and **application-aware defect qualification**.

---

## Why I am not presenting a token-savings percentage

The token economics are clearly important — repository-scale agentic analysis is consuming millions of context tokens — but this environment introduced too many uncontrolled variables for a defensible percentage claim.

Key issues observed:

- Cursor UI model selection and Usage telemetry did not agree.
- Cursor autonomously changed orchestration strategy between runs.
- Child sessions were spawned despite settings intended to constrain subagent behavior.
- Usage telemetry included `auto` and `composer-2.5-fast` events.
- The expected Synopsys scanner scripts were missing, so Cursor synthesized fallback workflows.
- TC-001B reused prior scan artifacts instead of performing a fully independent discovery pass.

**Message to emphasize:**

> The economics matter, but the final number needs to come from a customer-controlled test where model, orchestration, workflow assets, and telemetry are all verifiable.

---

## What Synopsys should do next

Run the final apples-to-apples benchmark in the Synopsys-controlled environment with the following controls:

1. Same CTS source/view in both arms.
2. Same verified Synopsys skill package and dependencies.
3. Same exact prompt.
4. Verified pinned model with authoritative telemetry — no ambiguous Auto routing.
5. Clean session/workspace for each arm, with no previous candidate/report artifacts available.
6. CoreStory disabled for baseline; CoreStory MCP + governing rule enabled for the comparison arm.
7. Held-out TSan/Coverity findings used only **after both runs** for scoring.
8. Capture runtime, fresh input/cache/output/total tokens, local tool calls, CoreStory calls, candidate count, final findings, and false-positive burden.
9. Repeat runs if necessary to quantify normal agent variability.

Then score:

- **Token/cost efficiency**
- **Time-to-result**
- **Recall against known defects**
- **Additional credible findings**
- **False-positive / reviewer burden**

---

## Close

What I would claim from these preliminary runs:

> We demonstrated the workflow, showed that repository-scale ND analysis has meaningful token economics, exposed several important Cursor/environment controls that affect benchmark validity, and saw a strong preliminary signal that CoreStory can improve defect qualification by bringing build, reachability, and application-context evidence into the analysis.

What I would **not** claim yet:

> A precise CoreStory token-reduction percentage or final defect-detection improvement.

That is what the Synopsys-owned apples-to-apples run should establish next.
