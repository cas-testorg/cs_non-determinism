# CTS Non-Determinism Evaluation — Preliminary Findings & Production Test Readiness

## Opening / framing

The goal of this exercise was to test the existing Synopsys nondeterminism workflow against CTS both **without CoreStory** and **with CoreStory**, while holding the user prompt and source scope as constant as possible.

The most important conclusion is not a defect-count or token-savings number. The preliminary work validated the workflow and showed where CoreStory appears most useful — **qualification and application-context reasoning** — while also exposing harness-level controls that must be fixed before making quantitative claims about recall, runtime, or token efficiency.

The decisive benchmark should still be run by Synopsys in a controlled environment.

---

## What we ran

### TC-001 — Initial baseline pilot

- CoreStory disabled.
- Same CTS repository and ND prompt.
- Run hit disk exhaustion and required human intervention.
- Expected `scan_nd.py` / `render_report.py` scripts were not installed, so Cursor substituted its own local search/triage workflow.
- Cursor UI showed Claude Opus 4.8, but Usage telemetry reported `auto`.

**Takeaway:** useful diagnostic evidence, but not a valid baseline.

### TC-001A — Baseline control

- CoreStory disabled.
- Same prompt and CTS scope.
- Disk issue resolved.
- Explore Subagent Model was disabled and the visible model was constrained.
- Cursor nevertheless created multiple child analysis sessions.
- Stage 1 produced **4,535 hits across 817 files**.
- Final report promoted **1 HIGH + 6 MEDIUM** findings.

**Takeaway:** completed baseline, but Cursor orchestration was not fully controllable.

### TC-001B — CoreStory + v2 rule

- Same prompt and CTS scope.
- CoreStory MCP enabled with `code-analysis-v2.mdc`.
- Synopsys skill installation left unchanged.
- Cursor reused prior local ND artifacts, so this was not a clean independent discovery run.
- Build, caller, reachability, and observability checks reduced the promoted set to **0 HIGH + 0 MEDIUM** confirmed equivalent-run defects.

**Takeaway:** strong directional qualification / false-positive-reduction signal, but not a clean A/B economics test.

### TC-001C — CoreStory + v3 rule check

- Intended change from TC-001B was the governing rule only: `code-analysis-v2.mdc` → `code-analysis-v3.mdc`.
- Same user prompt, CTS source, CoreStory connection, and Synopsys skills.
- v3 was tightened around build inclusion, production reachability, runtime gates, propagation, deterministic neutralizers, downstream observability, and investigation isolation.
- Cursor again created child/subagent analysis sessions despite the visible control settings.
- The installed scanner scripts were still absent, so Cursor again synthesized a ripgrep/PowerShell scanning workflow.
- The mechanical scan produced roughly **15,000 candidates** before narrowing.
- Child investigations showed stronger qualification-oriented behavior: promote only real/order-sensitive findings, check deterministic comparators and neutralizers, establish downstream observability, and use CoreStory for application context.
- The final findings changed again, but because Cursor changed execution topology, the result cannot be attributed to the rule alone.

**Takeaway:** v3 appears directionally better aligned with the intended qualification workflow, but TC-001C is a **rule-validation experiment**, not a controlled v2-vs-v3 benchmark.

---

## The most important finding

The harder problem is not generating suspects. It is determining **which suspects actually matter in the built application**.

The runs produced thousands of mechanical candidates. The useful signal came from qualification: build inclusion, reachability, active runtime path, propagation, deterministic normalization, and observable application impact.

A representative example is the baseline HIGH finding in `ctoFlowClone.cc`:

- Baseline analysis saw address-ordered `std::set<ndmTerm*>` iteration and promoted it as HIGH.
- The CoreStory-assisted pass checked the production build and found `ctoFlowClone.cc` was not included in `ctscto/Master.make`.
- The live production path instead uses `ctoRestruct.cc` and `termSetType`, with `ndmObjPtrCmpType` providing deterministic pointer ordering.

Another promoted candidate used `std::random_device`, but deeper qualification showed its only caller was commented out.

**Message to emphasize:**

> CoreStory did not simply produce a larger defect list. It added application context that changed which findings survived build, reachability, and observability checks.

This is the clearest preliminary value signal from the work so far.

## What TC-001C changed in our thinking

TC-001C helped separate the **rule problem** from the **test-harness problem**.

The v3 rule now makes the intended division of labor much clearer:

> Synopsys skills identify nondeterminism patterns and suspects. CoreStory supplies application context needed to determine whether those suspects are built, reachable, active, propagated, neutralized, and observable.

The v3 behavior was more consistent with that model. However, the largest remaining sources of experimental noise are outside the rule:

- missing skill scripts caused Cursor to invent a scanner,
- child/subagent sessions were created autonomously,
- model/orchestration telemetry remained difficult to control,
- and autonomous execution strategy changed between runs.

**Message to emphasize:**

> The rule is becoming more precise, but the next benchmark needs a more deterministic execution harness before we treat quantitative differences as causal.

---

## Why I am not presenting a token-savings percentage

Repository-scale agentic analysis is clearly consuming substantial context, so token economics remain important. But these runs introduced too many uncontrolled variables for a defensible percentage claim.

Observed issues included:

- Cursor UI model selection and Usage telemetry did not consistently agree.
- Usage included `auto` and `composer-2.5-fast` events.
- Cursor autonomously changed orchestration and spawned child sessions.
- The expected Synopsys scanner scripts were missing.
- One CoreStory run reused prior analysis artifacts.
- Request-level correlation was incomplete in some runs.

**Message to emphasize:**

> The economics matter, but the final number needs to come from a controlled test where model, orchestration, workflow assets, and telemetry are all verifiable.

---

## Recommended next move

Do **not** keep iterating tonight trying to produce a better-looking number from Cursor. Preserve these runs as preliminary evidence and use them to tighten the production benchmark.

For the next controlled test:

1. Verify the complete Synopsys skill package before execution; missing required scripts should fail preflight rather than trigger an improvised replacement workflow.
2. Use clean isolated workspaces with no prior ND reports, candidate files, or held-out ground truth available.
3. Separate **candidate discovery** from **candidate qualification** where practical. A fixed candidate set gives a much cleaner way to measure CoreStory's qualification value.
4. Use the same prompt, source revision, skills, and model in both arms.
5. Use CoreStory MCP + v3 only in the comparison arm.
6. Prefer an execution harness — potentially a command-line agent — where the exact model, orchestration behavior, MCP configuration, transcripts, and usage telemetry can be explicitly controlled and captured.
7. Score against held-out TSan/Coverity findings only after both arms are preserved.
8. Measure runtime, token usage, local search/read operations, CoreStory calls, candidate volume, verified defects, false-positive burden, and reviewer effort.

The strongest future experiment may be a two-stage test:

```text
Discovery -> fixed suspect set

Qualification A: same suspects + Synopsys proof workflow, no CoreStory
Qualification B: same suspects + same proof workflow + CoreStory v3
```

That isolates the exact value the preliminary work is pointing toward.

---

## Close

What I would claim from the preliminary work:

> We validated the workflow, demonstrated the scale of the candidate-filtering problem, identified several environmental controls that affect benchmark validity, and saw a meaningful directional signal that CoreStory application context improves defect qualification.

What I would **not** claim yet:

> A precise CoreStory token-reduction percentage, a controlled v2-vs-v3 improvement, or a final defect-recall advantage.

The next step is not another uncontrolled local run. It is a cleaner production benchmark that isolates discovery, qualification, and economics and gives Synopsys an apples-to-apples result they can trust.
